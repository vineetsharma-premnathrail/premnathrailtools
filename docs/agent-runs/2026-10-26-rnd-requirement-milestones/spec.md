# Milestones on an R&D Requirement (works the same as on an R&D Project)

Owner request (2026-10-26): "same milestone like in requirement". Owner decision (chat): a Requirement gets a **Milestones tab** like an R&D Project; **tasks sit inside milestones**; plan + history. The Tasks & Departments tab stays for department sharing. Existing tasks without a milestone keep working (shown as "No milestone").
Size L. Design by the architecture agent (read-only). One migration, new table, new router, generalised React component.

## Facts about the code
- An R&D Requirement is a CRM Inquiry or Tender sent to R&D. It has no table: it is addressed by `(source, record_id)`, `source` is `"inquiry"` or `"tender"` (`backend/app/modules/rnd/routes/requirement_work.py:71`). Tasks: `rnd_requirement_tasks` (`models/requirement_work.py`, `RndRequirementTask`, has `parent_task_id`). Access per record: `backend/app/modules/rnd/services/requirement_access.py` (`ra.ensure`, `ra.is_head`, `ra.is_rnd_side`, `ra.ensure_head`, department shares). Feature keys `rnd:requirements.<feature>`, checked only for R&D-side users.
- Project milestones: `backend/app/modules/rnd/models/project_milestone.py` (`RndProjectMilestone`, status constants RND_MILESTONE_STATUSES / _OPEN / _STATUS_LABELS / _ICONS), `routes/project_milestones.py`, tasks point to them by `rnd_project_tasks.milestone_id`. UI: `frontend/src/components/rnd/RndMilestonePlan.tsx` (684 lines), used by `frontend/src/app/dashboard/rnd/projects/[id]/page.tsx`.
- Requirement page: `frontend/src/app/dashboard/rnd/requirements/[source]/[id]/page.tsx` (tabs, TAB_FEATURE), `frontend/src/components/rnd/RequirementTasksTab.tsx`, department view `DeptRequirementDetail.tsx` (unchanged).

## Decision
Parallel table `rnd_requirement_milestones` (same columns and status machine as `RndProjectMilestone`) + nullable `rnd_requirement_tasks.milestone_id`; a new router that copies the project rules with "project lead" replaced by "R&D head" (`ra.is_head`); `RndMilestonePlan.tsx` generalised with props so the project and the requirement both use it. The project milestone table and routes are NOT changed. Rejected: making `rnd_project_milestones.project_id` nullable, or a generic polymorphic table.

## 1. Data (database-agent) - ONE migration
- New model file `backend/app/modules/rnd/models/requirement_milestone.py`, class `RndRequirementMilestone(Base, TimestampMixin)`, table `rnd_requirement_milestones`; import the status constants from `models/project_milestone.py` (do not redefine). Columns: id PK; `source` String(20) not null with CheckConstraint `ck_rnd_requirement_milestones_source` (`source IN ('inquiry','tender')`); `record_id` Integer not null (no FK, polymorphic like the tasks); `title` String(200) not null; `description` Text; `assignee_id` Integer FK users.id not null, indexed; `co_owner_ids` JSON (list of ints); `start_date` Date; `due_date` Date not null; `status` String(20) not null default and server_default `todo`; `blocker_reason`, `reopen_reason`, `cancel_reason` Text; `color` String(9); `icon` String(20); `created_by_id`, `completed_by_id` Integer FK users.id nullable; `completed_at` DateTime(tz); created_at/updated_at from the mixin. Indexes `ix_rnd_requirement_milestones_source_record` on (source, record_id) and `ix_rnd_requirement_milestones_assignee_id`. No sort_order (timeline ordered by due_date, id; cancelled last).
- Change `RndRequirementTask` in `models/requirement_work.py`: `milestone_id: Mapped[int | None] = mapped_column(Integer, ForeignKey("rnd_requirement_milestones.id", ondelete="SET NULL"), index=True, nullable=True)`. No back-fill.
- Migration `backend/alembic/versions/<rev>_rnd_requirement_milestones.py`, `down_revision` = the single head at launch (run `alembic heads`; it is d1f6b4a8c3e5 now and is already applied locally). Guard every create with the inspector like the repo's recent migrations; downgrade in reverse. Nullable column without default = metadata-only change. Do NOT run `alembic upgrade`, never touch a database.

## 2. API (backend-agent) - new `backend/app/modules/rnd/routes/requirement_milestones.py`
Router `APIRouter(prefix="/requirement-work", tags=["RnD Requirement Milestones"], dependencies=[Depends(_require_requirement_side)])`, mounted by the Manager at `/api/v1/rnd` (the same prefix as the existing requirement-work router). Import `_require_requirement_side`, `_record`, `_ref`, `_notify`, `_name` from `routes/requirement_work.py`. `RULE_KEY = "rnd:requirements.milestones"`.
Every endpoint: (1) `_record(db, source, record_id)` or 404 "This {source} no longer exists in CRM or hasn't been sent to R&D - refresh the Requirements list."; (2) `ra.ensure(db, user, source, record_id, "view")`; (3) if `ra.is_rnd_side(user)` also `ensure_feature_action(user, "rnd", "requirements", <feature>, <action>)` (department-side users: record rules only, like the existing task routes); (4) the milestone is looked up by BOTH `source` and `record_id` or 404 "Milestone #{mid} isn't on {ref} any more - refresh the page." (stops IDOR).
Endpoints (prefix `/requirement-work`):
- GET `/{source}/{record_id}/milestones` (milestones/view) -> list
- GET `/{source}/{record_id}/milestone-people` (milestones/view) -> `[{id, name, department, designation, team_role: "head"|"member"}]`, deduplicated, people of `ra.working_departments`, filtered by `assignee_rules.filter_people(RULE_KEY)`
- POST `/{source}/{record_id}/milestones` (milestones/create; head only)
- PATCH `/{source}/{record_id}/milestones/{mid}` (milestones/edit; head only)
- POST `/{source}/{record_id}/milestones/{mid}/status` body `{action: "done"|"reopen"|"cancel", reason?}` (milestone_status approve/edit/cancel; done: head or an owner; reopen and cancel: head, reason required)
- DELETE `/{source}/{record_id}/milestones/{mid}` (milestones/delete; head only, only while the milestone never had a task; otherwise 409 "Use Cancel milestone instead")
- GET `/{source}/{record_id}/history` (history/view; R&D side only, department side gets 403 "History is on R&D's requirement page") -> `[{id, kind: "milestone"|"requirement"|"task", action, summary, performed_by, performed_at}]` from `AuditLog` where `entity_type == f"rnd_req_{source}"` and `entity_id == record_id` (limit 500) plus `RndTaskEvent` of the requirement's tasks (reuse `TASK_VERBS`); non-heads do not see audit rows whose action starts with `access_`.
`MilestoneIn` = the project version (title, description, assignee_id, co_owner_ids, start_date, due_date, status in todo/in_progress/blocked, blocker_reason, color, icon). Response `RndMilestone` = the project `serialize()` shape with `source` and `record_id` instead of `project_id`; flags `can_edit` = is_head, `can_work` = head or owner, `can_plan` = milestone open and user has view access, `can_delete` = head and never had a task; progress = top-level tasks not cancelled.
Validation / messages (copy the project version; "project lead of X" becomes "Only the R&D head ({names}) or an admin can {what}. R&D heads are the R&D department's heads in Organization > Department." via `ra.ensure_head`): owner must be active and belong to a working department (R&D owners need the `rnd` app; department owners `can_see_department`) else 422 "{name} doesn't work on this requirement - pick someone from R&D or a department it is shared with (share it from Tasks & Departments first)."; `assignee_rules.ensure_allowed(RULE_KEY)`; end date required, start not after end; changing the end date earlier than an open task's due date -> 422 listing up to 3 tasks; done -> 409 if any task is still `open` (names them); cancel -> 409 if any open task; a new R&D owner gets `ra.grant_task_access(...)` so they can open the requirement.
Audit (`record_audit`, `entity_type=f"rnd_req_{source}"`, `module_key="rnd"`): milestone_created / _updated / _achieved / _reopen / _cancel / _deleted / milestone_reopened_by_task. Notifications via the requirement `_notify`, types `rnd_requirement_milestone_assigned/_edited/_achieved`, bell only. No approval engine.
Task flow changes in `routes/requirement_work.py` (rules unchanged, milestone only adds checks): `_serialize_tasks` adds `milestone_id` and `milestone_title`; `create_task` takes `milestone_id: int | None = Form(None)` (milestone must be open and on the same requirement else 409 "Milestone '{t}' is {status}, so it can't get tasks. Reopen it first, or pick another milestone."; due date must fit the milestone end else 422; a `todo` milestone becomes `in_progress`; who may create does not change); `create_subtask` copies the parent's `milestone_id`; `edit_task` accepts `milestone_id` (moving a main task into a milestone is head-only; target open, same requirement, due date fits; sub-tasks move with the task, moving a sub-task alone -> 409 "A sub-task stays in its main task's milestone - move the main task instead."); changing the due date of a task inside a milestone is re-checked; `extend_task` (assignee re-dates an overdue task) has NO milestone check; `reopen_task`: if the task's milestone is `done`, set it back to `in_progress`, clear completed_*, audit `milestone_reopened_by_task`, notify owners.
Feature registry `backend/app/core/features/rnd.py` (requirements group, re-read first): `_feature("milestones", "Milestones", "subtab", {"view": "view", "create": "view", "edit": "view", "delete": "view"}, ...)`, `_feature("milestone_status", "Achieve, reopen & cancel milestones", "action", {"view": "view", "approve": "view", "edit": "view", "cancel": "view"}, ...)`, `_feature("history", "History", "subtab", {"view": "view"}, ...)`, `register_pickers("rnd", "requirements", ("milestones", "Set milestone owners to", "Who this role may make responsible for a requirement milestone (R&D or a shared department)."))`. All inherit `view`, so current roles keep access.
Tests `backend/app/tests/test_rnd_requirement_milestones.py`: head create/edit/delete, non-head 403, no-view 403; milestone from another requirement or source -> 404 everywhere incl. create_task/edit_task; owner not in a working department 422, assignee rule 403, new R&D owner gets access; closed milestone 409, date after end 422, first task moves todo->in_progress, sub-task inherits; achieve with open task 409, owner achieves, reopen/cancel need reason, cancel with open tasks 409, delete after any task 409; end date before an open task 422; reopening a task in an achieved milestone re-opens it + audit; move between milestones head-only, sub-tasks follow; legacy tasks (milestone_id NULL) behave as before (existing `test_rnd_requirement_work.py` passes unchanged); history merges audit + task events and hides `access_*` from non-heads; feature gate for R&D-side roles; department-side users not feature-gated.

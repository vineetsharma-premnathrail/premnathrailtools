# Upgrade & Migration Guide

This guide documents how schema changes are actually made in this repo
(Alembic conventions observed across current migration files) and how to
apply/roll them back safely.

## No formal frontend/backend deployment coordination

There is no version-pinning or compatibility matrix anywhere in the repo
tying a given frontend build to a given backend build — no shared version
constant, no API version header check, no "minimum backend version"
constant in the frontend, nothing of that kind. Frontend and backend live in
the same monorepo and are deployed together as a single container (see the
consolidated Dockerfile / `docker-entrypoint.sh`, added in commit
`c264408`), so in practice they are always upgraded in lockstep — but that's
an artifact of the deployment topology, not an explicit compatibility
contract enforced in code. If frontend and backend are ever split into
independently deployed services, this is a gap that will need addressing.

## The house convention: idempotent, existence-checked migrations

Every recent migration under `backend/alembic/versions/` follows the same
defensive pattern: **before adding a column or table, check whether it
already exists**, using `sa.inspect(op.get_bind())`. This makes migrations
safe to re-run against a database that may already be partially migrated
(e.g., from a previous failed run, or a database that diverged from the
alembic version table for any reason).

Confirmed in multiple files, e.g.
`backend/alembic/versions/f2a7c5e9d1b3_add_private_project_attachments.py`:

```python
def upgrade() -> None:
    """Upgrade schema."""
    inspector = sa.inspect(op.get_bind())
    existing_columns = {c["name"] for c in inspector.get_columns("erp_project_attachments")}
    if "is_private" not in existing_columns:
        op.add_column(
            "erp_project_attachments",
            sa.Column("is_private", sa.Boolean(), nullable=False, server_default=sa.false()),
        )

    if "erp_project_attachment_shares" not in inspector.get_table_names():
        op.create_table(
            "erp_project_attachment_shares",
            ...
        )
```

The same pattern appears in
`backend/alembic/versions/e7c1a9d4f256_add_pr_category_requirement_approver.py`
(checks each of `category_code`, `requirement_type`, `approver_id`,
`approver_name` individually before adding) and in
`backend/alembic/versions/a5d2f8c1e4b7_add_department_designation_shares.py`
(checks columns via `inspector.get_columns(...)` and checks for an existing
unique constraint via `inspector.get_unique_constraints(...)` before
attempting to drop it). Note that in that last file, `op.alter_column(...)`
to make `user_id` nullable is run unconditionally — the idempotency guard is
applied selectively, to the operations that would actually fail on rerun
(add an existing column, drop a nonexistent constraint), not blanket-applied
to every line.

**When writing a new migration, follow this convention**: inspect the
target table/columns/constraints with `sa.inspect(op.get_bind())` first, and
only issue the DDL operation if the guard shows it hasn't already happened.
`downgrade()` functions in these files are written unconditionally (plain
`op.drop_column` / `op.drop_table` / `op.create_unique_constraint`) — the
idempotency guard is an `upgrade()`-only convention in this repo.

## Standard workflow

### 1. Make your model change

Edit the SQLAlchemy model(s) under `backend/app/modules/*/models/`.

### 2. Generate a migration

```bash
cd backend
alembic revision --autogenerate -m "add <thing>"
```

### 3. Review and edit the generated file

Autogenerate often gets things partially right (and sometimes wrong,
especially with `server_default`/constraint names). Edit it to:

- Add the `sa.inspect(...)` existence-check guard around `add_column` /
  `create_table` calls, per the convention above.
- Write a real `downgrade()` — don't leave the autogenerated stub if it's
  incomplete.
- Set a sensible `Create Date` docstring line and confirm `down_revision`
  points at the current head (`alembic heads` before generating, to catch
  multiple-heads situations early).

### 4. Apply it

```bash
alembic upgrade head
```

### 5. Verify

```bash
alembic current
```

Should show your new revision as current.

### 6. If something's wrong, roll back one step

```bash
alembic downgrade -1
```

Fix the migration file, then `alembic upgrade head` again. Because of the
existence-check convention, re-running `upgrade head` after a partial
failure is expected to be safe rather than erroring on "column already
exists."

## Rolling back further / to a specific revision

```bash
alembic history                  # see the full chain with revision IDs
alembic downgrade <revision_id>  # roll back to a specific point
```

`down_revision` chains are linear in this repo (single-parent, no observed
branch points as of this writing) — check `alembic history` if that ever
changes, since a branched history changes how `downgrade` targets are
resolved.

## Applying migrations in different environments

- **Local dev**: run `alembic upgrade head` manually after pulling backend
  changes (see `MAINTENANCE_PROCEDURES.md`) — `start-servers.bat` does not
  do this for you.
- **Container/production**: `docker-entrypoint.sh` runs
  `alembic upgrade head` automatically on every container start, before
  uvicorn is started. This means a bad migration will fail the container
  startup outright (the entrypoint uses `set -e`) rather than silently
  running against a mismatched schema — treat a container that fails to
  start after a deploy as "check the migration first."

## Before running a migration that drops or renames data

Take a manual backup first — see `backend/db_backups/` for the existing
convention (timestamped `.sql` dumps named for the migration they precede,
e.g. `pre_purchase_migration_20260730_162406.sql`). There is no automated
backup step wired into the migration workflow; it's a manual habit observed
in this repo's history, not an enforced step.
